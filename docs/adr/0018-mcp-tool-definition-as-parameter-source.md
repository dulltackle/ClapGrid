# 业务 MCP 工具定义是参数的唯一来源

日期：2026-11-07

状态：已采纳（[#305](https://github.com/dulltackle/ClapGrid/issues/305)）。字段级说明是否迁移到 zod `.describe()` 由 [#314](https://github.com/dulltackle/ClapGrid/issues/314) 另行评估。

## 决策

业务 MCP 工具的调用形状，包括参数对象、字段含义、取值范围和数量上限，只在 `src/mcp/server.ts` 的工具定义（`inputSchema` 与 `description`）中维护。agent 调用时读到的正是这份定义。

文档之间按读者和内容分工：

- README 面向使用者并作为维护者的导航入口，不复述参数，也不复述产品契约中的行为规则，只链接到对应章节。工具只按用途分组列出名称。
- `docs/product-contract.md` 维护行为规则，工具与参数链接到工具定义。
- `composition.md` 等随插件发布的制作约定维护规则、流程和语义，提到工具时只写名称，不写参数对象。“导入边界”属于页面和风格作者的编写约束，例外保留在该文档中。
- 模块职责写在源码文件头部的注释中。HTTP 端点以路由代码为准，不在文档中列举。

工具描述中保留简短的规则提醒，作为调用时的安全栏，例如编排要求背景连续覆盖、合成预览只有 `succeeded` 且 `current` 时才可审阅。规则的权威来源仍是制作约定和产品契约：两边措辞不一致时以规则文档为准，修改规则时同步修改提醒。文档中出现的 `clapgrid_*` 工具名由文档检查核对是否已注册，参数不做机械比对。

## 否决的方案

- **另建 MCP 参考文档并随插件发布**：在工具定义之外多一份需要手工同步的副本，而 agent 已能直接读到工具定义。README 原有的参数说明正是这样逐渐过时的：缺少素材归属、编排、画面说明和批量配音，且没有跟上面板关联的语义变化。
- **工具描述只指向规则文档，不写任何规则**：agent 调用工具时不一定读过制作约定，可能跳过关键约束。
- **不拆，只修正 README**：保留了同一份内容的多处复述，下次修改工具或行为时仍会漂移。
