# Codex 插件本地运行与项目访问边界研究

研究日期：2026-09-21。对应事项：[验证 Codex 插件的本地表格运行与项目访问边界](https://github.com/dulltackle/ClapGrid/issues/2)。本轮是资料与环境研究，没有运行 UI 原型；以下建议不代表已经锁定的平台决策。

## 结论

“Codex 插件入口 + 本地表格 + 本地项目”存在可行候选路径，但不能把插件目录中的 `ui/` 当作已获宿主承诺的扩展点。建议下一步验证由本地服务提供浏览器表格、由插件提供 Skill 与 MCP 的组合。若用户要求表格必须是宿主内嵌组件，则需要单独验证当前客户端兼容性。

## 已确认事实与依据

- 官方插件架构将 Skill、MCP 和可选 UI 组合；能力可能因产品界面而异。它没有承诺扫描任意 `ui/` 目录并安装原生面板。[插件架构](https://developers.openai.com/plugins/concepts/plugins)
- 官方 MCP 文档支持启动本地进程的 STDIO，以及通过 URL 访问的 Streamable HTTP；STDIO 可设置 command、args、env、cwd。文档明确包含桌面客户端配置步骤。[MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)
- 官方 UI 页面描述的是 ChatGPT 中的 iframe，经 MCP Apps 桥接调用工具；核心数据不应依赖 iframe 的 localStorage，组件加载与联网受 CSP 限制。因此不能把该页面直接解释为所有 Codex 客户端已支持相同的本地文件、媒体与组件行为。[为 MCP 添加 UI](https://developers.openai.com/plugins/build/chatgpt-ui)
- 本地 marketplace 与公共目录是不同分发路径；插件安装到缓存副本，而非一直从开发目录读取。故项目数据库、媒体和用户密钥不能存放在插件安装目录。[插件打包](https://developers.openai.com/plugins/build/plugins)
- 当前环境可见 `mcp__codex_app__open_in_codex` 工具的浏览器 URL 入口。这是当前会话能力证据，不是任意第三方插件或其他版本均可调用的公共保证。

## 最小候选运行方案（工程建议，待平台决策）

```text
Codex Skill → STDIO MCP 适配器 ─┐
                              ├→ 单个本地项目服务 → SQLite / 项目媒体 / 任务执行
浏览器中的表格 → 本地 HTTP API ┘
```

1. 一个本地服务同时提供静态表格页面、业务 API 和媒体访问；MCP 适配器把有业务语义的调用转给同一服务。浏览器不直接打开数据库，避免两套写入逻辑。
2. 启动器按规范化项目路径复用服务实例，用锁和健康检查避免两个 Codex 任务启动两个执行者。项目标识显式传递，不把插件缓存目录或任意工具当前目录当作项目。
3. 服务仅监听 loopback；写接口校验会话令牌与来源。浏览器上传文件内容，或 MCP 从明确授权的导入路径复制素材。已入库素材按 ID 提供媒体路由，解析真实路径并检查范围，避免暴露任意文件路径读取接口。
4. 媒体由服务流式提供，支持浏览器拖动播放需要的范围请求；先验证输入编码与浏览器兼容性。`file://` 绝对路径不作为可移植播放方案。需要时生成预览副本，原文件仍保存在项目中。
5. 配音与导出返回任务 ID，由服务持有持久化任务记录；表格轮询即可满足小规模场景。关页不等于取消任务；服务退出后将进行中任务恢复为可检查的中断状态，付费配音不盲目自动重发。
6. 导出使用文案、配音与素材引用的快照，提交结果时校验版本；共同业务层并不能自动消除并发覆盖。

这些是适合该场景的设计建议，不是官方文档替项目提供的能力。无需因旧方案的万条规模引入多服务、分布式队列或额外数据同步层。

## 生命周期与尚未验证的边界

- 未验证当前客户端中 MCP Apps 组件的实际渲染、文件选择、localhost 访问和音视频播放；本次没有把文档支持冒充端到端测试通过。
- 未验证关闭 Codex、重启 MCP、切换任务时子进程的具体存活行为。长任务不能依赖未知的宿主进程生命周期；应由明确的本地服务生命周期和持久化状态保证恢复。
- 未验证当前版本自动打开本地 UI 的完整路径；可先提供普通 localhost 链接，但是否允许外部浏览器需要用户决定。
- 浏览器与文件所在机器必须匹配；远程执行环境中的 localhost 不自动等于用户桌面 localhost。远程开发和云端 Codex 暂不可纳入“自然就支持”。
- 数据库和文件仍需应用自己的范围检查；本会话 shell 沙箱不是所有 MCP 服务的通用访问控制证明。
- Node、ffmpeg、字体和密钥存储的安装方式取决于首发 OS。当前 Linux 可用并不能证明 macOS、Windows 或其他 Linux 环境开箱可用。

## 留给用户的平台决策

1. 首发只服务哪一种系统与 Codex 客户端？当前 Linux 环境不是用户已确认的发布目标。
2. “Codex 插件入口”是否允许打开本地浏览器页面？若必须留在宿主内，应优先做兼容性原型，再锁定 UI 承载方案。
3. Codex 关闭后，配音与导出应继续，还是允许中断并在重新打开时恢复？这决定本地服务是否需要独立常驻。

## 后续最小验证范围

平台选择后，用两个口播片段验证：插件打开表格、两端编辑同步、本地导入与媒体播放、关页后任务可查询、宿主重启后的中断恢复。此处仅提出验证题目，不在研究事项内实施原型或替用户锁定平台。
