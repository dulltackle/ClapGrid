# Agent 协作规范

## 沟通规则

- 与开发者沟通时，始终使用中文。
- 回答问题、解释方案、汇报进展时，统一使用中文。
- 编写文档、注释说明、交付说明等面向开发者的内容时，统一使用中文。
- 生成 Git commit message 时，统一使用中文。

## Git 提交规范

### 基本原则

- 不执行破坏性 Git 操作，例如强制推送、硬重置；配置修改按下方具体风险与授权范围判断。
- 不主动绕过钩子，例如 `--no-verify`、`--no-gpg-sign`，除非用户明确要求。

### 提交范围规则

- 如果同时存在已暂存和未暂存更改，只提交当前已暂存文件。
- 如果只有已暂存更改，只分析并提交已暂存内容。
- 如果没有已暂存文件，则分析全部未跟踪和未暂存文件，并在确认后统一暂存提交。
- 不得改变用户已有的暂存集合。

### 提交消息规范

使用 Conventional Commits 格式：

```text
<type>: <description>

[body]

[optional footer(s)]
```

常用类型：

- `feat`：新功能
- `fix`：Bug 修复
- `docs`：文档更改
- `style`：格式调整
- `refactor`：重构
- `perf`：性能优化
- `test`：测试相关
- `build`：构建或依赖
- `ci`：CI 配置
- `chore`：其他维护
- `revert`：回滚提交

## 配置修改与授权续接

- 修改前确认目标文件、影响范围、是否涉及凭据、权限、外部服务或费用，并保存可恢复的原文或精确差异。只定向修改本次需要的配置，不批量替换用户配置。
- 同一会话或可核实续接记录中已有授权，且目标、内容和影响范围未实质变化时继续执行，不重复索取相同授权。记录授权内容、适用范围和完成证据，续接时核对当前状态。
- 新增费用、扩大权限、修改无关配置或需要丢弃用户内容时，先完成不依赖该决定的准备工作，再说明具体变化并请求用户决定；无法核实原授权时说明缺失内容。
- 用户授权与宿主审批分别核对。规则修改不扩大工具权限，也不能绕过宿主审批；受保护路径使用宿主审批入口，拒绝时保留成果并报告原因，不换路径或工具规避拒绝。

## 临时工作树清理

1. 根据本轮记录确认工作树路径、创建归属和恢复引用；仅纳入本轮临时工作树，排除无关工作树。项目主目录、共享工作树及工具标记不可清理对象保持原状。
2. 核实成果已集成，或存在已验证可恢复的提交、备份；记录集成提交或恢复位置。再检查暂存、未暂存、未跟踪、被忽略文件及编辑器未保存结果，不能仅凭 Git 状态干净认定没有未保存成果。
3. 有未保存成果时先保存并验证可恢复性；遇到需要丢弃内容或归属不明时暂停该对象并请求用户决定，其他对象可独立继续。
4. 已满足保存条件且已有本轮清理授权时，沿用授权执行正常清理；缺少清理授权时先呈现具体路径、保存证据和处理计划，再请求决定。使用创建该工作树的管理入口；普通 Git 工作树使用正常移除流程，不强删、不硬重置。
5. 每次清理仍遵守宿主审批；被拒绝时保留工作树、恢复引用和阻塞原因。记录实际清理结果及剩余路径，不能以规则已修改宣称目录已清理。
