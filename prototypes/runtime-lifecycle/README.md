## 运行与数据

需要 Python 3（本机实测 3.12.3）；随附 sample.mp4 是 ffmpeg 合成的四秒测试图案与轻音，无外部素材。

在仓库根目录运行：

```bash
python3 prototypes/runtime-lifecycle/prototype.py
```

Windows 可使用 `py -3` 替代 `python3`，但尚未实测。启动器返回 URL，由 Codex 打开到右侧内置浏览器：`http://127.0.0.1:48761/`。同一端口与项目重复启动会连接已有服务。临时项目默认是系统临时目录中的 `clapgrid-PROTOTYPE-wipe-me`；文件名为 `PROTOTYPE-state.json`，可通过 `--project` 指定其他专用测试目录。不要指向真实项目。默认临时目录可能被系统清理，不代表产品项目的持久化方案。

服务只监听 127.0.0.1。原型按同源 JSON 限制写入；没有生产级鉴权和完整多客户端并发处理。固定端口只保证此原型默认实例唯一，不代表跨端口、跨项目的生产单实例机制。

页面可启动三分钟无费用模拟任务、编辑两段测试文案、查看完整状态，并明确中断任务和退出服务。无任务时点击“退出服务”即可停止。重启仍使用上方命令。

## 已完成体验的复测步骤

1. 打开原型，点击“开始 3 分钟模拟任务”，记下任务 ID。
2. 完全退出 Codex 桌面应用，等待约 20 秒后重开（不是仅关闭面板）。
3. 请 Codex 先读取 `http://127.0.0.1:48761/state`，再运行启动器；先读可以区分原服务存活和服务重建。
4. 记录任务 ID、PID、进度和状态。如果服务停止或任务显示已中断，则“完全退出后继续”没有通过。
5. 反馈实际结果和可协助验证的其他系统。媒体崩溃需单独复现定位；首次安装链路需后续提供安装原型实测。

## 媒体复测（2026-09-25）

用户要求现在测试视频。测试开始时本地服务不可连接，因此重新启动已有原型服务；没有启动或重试模拟任务。该启动前状态不改变用户此前报告的生命周期体验结果，服务何时、为何停止本轮未调查。

在当前 Ubuntu 内置浏览器打开页面，点击测试媒体的播放按钮，浏览器再次显示 `This page crashed`。当前页面采用 `preload="none"`，说明仅关闭预加载并未解决播放时崩溃。播放判为失败；拖动因页面崩溃无法执行，判为受阻。

辅助核对：ffmpeg 完整解码随附 MP4 无报错；媒体接口对 `Range: bytes=0-1023` 返回 206，Content-Range 为 `bytes 0-1023/416312`，Content-Length 为 1024；崩溃后 `/state` 仍可访问。因此当前证据未显示文件无法解码或后台服务停止，但尚不能确定浏览器崩溃根因，也不能把接口范围请求通过当作浏览器拖动通过。未确认实际声音输出。

## 本轮诊断与实际插件安装（2026-09-25）

详见 [媒体诊断记录](media-probe/RESULTS.md)。已保留原 MP4，同时增加 `preview.webm`（VP8 + Opus）作为当前宿主的候选预览路径。固定 MP4 成片要求不变。未修改宿主 GPU 或安全设置。

纠正此前归因：无障碍接口直接点击原生媒体播放按钮会触发渲染进程崩溃（日志 exitCode=4），即使可正常播放的 VP8 也如此；鼠标坐标点击同一 VP8 控件可正常播放。所以此前“点击播放即崩溃”不能直接当作用户鼠标操作结果。但 H.264/VP9 经普通 HTML 按钮启动仍独立出现解码错误，问题并非全由自动化点击引起。

使用 plugin-creator 与 writing-for-agents 技能创建插件，manifest 和 SKILL 校验通过。通过 CLI 安装 `clapgrid-runtime-probe@personal`，实际缓存位置为 `/home/forclaw/.codex/plugins/cache/personal/clapgrid-runtime-probe/0.1.0`。缓存脚本、技能、页面、预览资产均与打包源一致；停止无任务的原服务后，从该缓存启动新进程并恢复临时项目，通过 HTTP 和内置页面回归。已从缓存重复执行启动器验证复用已有服务。

安装步骤使用本机已有 Python 3；尚未验证无 Python 的首次组件安装，也未实现自动安装运行时。后台启动使用宿主执行审批；不把这记为无审批自动启动保证。

本地可分发快照为 `clapgrid-runtime-probe.zip`，含插件 manifest、技能、脚本、页面和测试媒体。这是一次性验证插件，不是产品交付。原型源码与证据仍未提交，不合入主分支。

## 安装后新任务验收与冷启动复测（2026-09-25）

本节为最新结果；上文媒体失败与安装入口未验证等描述保留为历史过程，以本节和三平台矩阵为当前结论。

- 环境：Ubuntu 24.04.5 LTS、Linux 7.0.0-34-generic x86_64、Python 3.12.3；用户确认 Codex Version 26.917.71314。
- 用户在本任务显式调用已安装的 `clapgrid-runtime-probe` 技能，代理读取安装缓存技能并执行缓存中的 `scripts/prototype.py`，没有依赖仓库脚本启动。
- 启动前读取 `/state`，随后启动器复用 PID `288387`；独立调用核对服务仍在线。宿主 `open_in_codex` 使用 `placement: right`、browser URL 返回 queued，此时未判成功。用户随后确认页面 VP8 视频播放与拖动正常，补齐实际页面体验证据。没有把当前宿主能力泛化为三平台公开接口保证。
- 用户退出前已有任务 `70ddcfd5-ffd1-49c2-a58a-e0669dfe9dd7` 正在运行，因此没有新建重复任务。基线 PID `288387`、进度 `142/180`、运行中且 `locked: true`。
- 用户按步骤退出并回复“已重开”后，代理先读 `/state`，未运行启动器：PID 和任务 ID 均未变化，进度 `180/180`、已完成。表明旧服务存活、同一任务继续完成。关闭面板与完全退出为本轮合并验证，未单独采样；期间锁的持续性沿用先前独立验证，不把完成后的解锁当作失败。
- 随后在任务已完成时正常退出空闲服务，确认 `/state` 不可连接，再从缓存冷启动。默认沙箱内 PID `4` 在启动调用内可访问，但下一次独立 curl 返回连接失败（退出码 7）。按宿主审批机制以 `require_escalated` 启动后 PID `340896` 可跨调用存活，再次执行缓存启动器复用同一 PID。文案和已完成任务保留，没有重新执行任务。

结构化证据：[evidence-installed-session.json](evidence-installed-session.json)。跨平台复测规程：[VALIDATION.md](VALIDATION.md)。

当前判断：所选方案在本机 Ubuntu 的已安装插件路径上可行，但后台冷启动依赖宿主执行审批。Windows/macOS（已拆分至 #11/#12 留待以后测试）、缺少 Python 的首次组件安装仍未验证；音频听感也未单独确认。尚无证据要求降低三平台或右侧面板要求，#10 保持开放。
